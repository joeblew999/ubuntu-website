## ひとつの言語。あらゆる出力。あらゆる言語。

シングルソースのコンテンツ管理システム。すべてをひとつのDSLで定義します—**すべての2Dおよび3D出力を駆動するテキスト（1D）**。コンポーネントを含むコンポーネントを組み合わせます。あらゆるチャネルへ出力。あらゆる言語へ自動翻訳。データを取り込んで戻します。

すべてWeb対応。すべて世界中からアクセス可能。完璧なブランディング—規律によってではなく、アーキテクチャによって。

---

## 課題

組織はコンテンツを複数のチャネルで公開しています：Webサイト、PDF、メール、フォーム、サイネージ。

各チャネルは個別に管理されています。コンテンツは食い違い、ブランディングは崩れ、翻訳は遅れ、フォームの送信内容は手作業で再入力されます。

**ひとつの変更のために5つのシステムを更新する。あるいは、まったく更新されない。**

---

## ひとつのDSL

すべてが同じ言語で定義されます。

**テキストコンテンツ：**
```
# Welcome to Our Service

We help organizations {industry} achieve {outcome}.
```

**グラフィックス：**
```
@logo: svg {
  viewBox: "0 0 200 50"
  rect: { x: 0, y: 0, width: 50, height: 50, fill: "#2563eb" }
  text: { x: 60, y: 35, content: "Ubuntu", font: "bold 24px" }
}
```

**フォームフィールド：**
```
Name: [_______________]{field: name, required: true}
Email: [_______________]{field: email, type: email}
Date: [__/__/____]{field: date, type: date}
```

**メール：**
```
@welcome-email: email {
  to: {customer.email}
  subject: "Welcome, {customer.name}"
  body: include welcome-content
}
```

**ひとつの言語で、テキスト、グラフィックス、フォーム、メール、ドキュメントを。**

## 組み合わせる

コンポーネントがコンポーネントを含みます。

```
@header: compose {
  include: logo
  include: navigation
  include: search-bar
}

@page-template: compose {
  include: header
  include: content
  include: footer
}

@welcome-letter: compose {
  include: page-template
  content: "Dear {customer.name}, welcome to..."
}

@application-form: compose {
  include: page-template
  content: include form-fields
}
```

**カスケード：**
- ロゴを変更 → ヘッダーが更新
- ヘッダーが更新 → すべてのページが更新
- すべてのページが更新 → すべてのPDF、メール、フォームが更新

**だからこそ、ブランディングは完璧に保たれます。** 誰かがすべての更新を忘れずに行うからではありません。アーキテクチャ上、更新されないことがあり得ないからです。

既存のあらゆるコンテンツにリンク。システム全体で再利用。信頼できる唯一の情報源。

## 出力

ひとつのソースから、すべてを生成します：

| 出力 | 何が起こるか |
|--------|--------------|
| Webページ | HTMLにレンダリング、SEO対応 |
| PDF | 印刷対応、アーカイブ用 |
| メール | 受信者へ直接送信 |
| Webフォーム | インタラクティブ、データを取り込んで戻す |
| PDFフォーム | 入力可能または印刷可能、OCRで取り込み |
| SVGグラフィックス | ベクターアセット、任意のサイズ |
| 地図 | あなたの位置データを可視化 |
| キオスク | 物理ディスプレイ、リアルタイム |

**すべての出力が自動翻訳されます。**

英語で書く。ドイツの同僚にはドイツ語で。スペインのパートナーにはスペイン語で。日本のお客様には日本語で表示されます。

事後に翻訳するのではありません。レンダリングの一部として翻訳されます。あらゆる出力を。あらゆる言語で。自動的に。

## 翻訳

翻訳は機能のひとつではありません。システムの動作そのものです。

| 機能 | 意味 |
|------------|---------------|
| エディタ内でリアルタイム | 複数の言語で同時にコラボレーション |
| 出力の自動翻訳 | あらゆる形式をあらゆる言語でレンダリング |
| オフラインAI | インターネットなしで動作 |
| 文脈認識 | 教育・法務・医療の用語を区別 |
| 双方向 | 相手は自分の言語で編集し、あなたは自分の言語で閲覧 |

**一度書けば、あらゆる言語で公開。**

## 取り込み

フォームはデータを取り込んで戻します。フォームを生成したのは私たちなので、すべてのフィールドの位置を正確に把握しています。

| チャネル | 何が起こるか |
|---------|--------------|
| Webフォームの送信 | データがあなたのデータベースへ流れる |
| PDFフォームをデジタルで入力 | データが抽出され、あなたのデータベースへ |
| PDFフォームを印刷し、手書きで記入してスキャン | OCRであなたのデータベースへ取り込み |

OCRのトレーニングは不要。フィールドマッピングも不要。フォームを生成したのは私たち—すべての位置を把握しています。

**紙でもデジタルでも。同じデータ。同じ保存先。**

## ヒューマン・イン・ザ・ループ：リアルタイムの現場業務

Publishは静的なドキュメントのためだけのものではありません。現場作業員がリアルタイムでシステムとやり取りするための手段です。

### フル活用されるデバイス

すべての現場作業員のデバイスが、センサーとディスプレイの両方になります：

| 入力（現場から） | 出力（現場へ） |
|--------------------|-------------------|
| GPS位置情報 | ルートマップ、ターンバイターン案内 |
| 音声コマンド（SST） | タスク通知 |
| タッチ操作 | スケジュール更新 |
| フォーム送信 | 確認アラート |
| カメラ（写真/動画） | ステータス表示 |

システムはすべての作業員の位置を把握しています。作業員は音声、タッチ、フォームを通じて応答できます。

### 2D出力

Publishはすべての2Dコンテンツ—Web、ドキュメント、地図、ディスプレイ—をレンダリングします：

| 出力 | ユースケース | 例 |
|--------|----------|---------|
| **Webページ** | 顧客ポータル、ステータス追跡 | サービス状況、注文追跡 |
| **ルートマップ** | ナビゲーション、配送追跡 | ごみ収集、配送先 |
| **ダッシュボード** | ステータス概要、KPI | 配車コンソール、チームのパフォーマンス |
| **ドキュメント** | 作業指示書、レポート、フォーム | PDFマニフェスト、コンプライアンス用エクスポート |
| **キオスク** | 公共ディスプレイ、チームボード | 拠点の状況、レストランのメニュー |

**3D空間の可視化**—建設現場、倉庫、デジタルツイン—については、[Spatialプラットフォーム](/platform/spatial/)をご覧ください。

### 音声による更新

音声テキスト変換（SST）により、ハンズフリーでシステムを操作できます：

| 作業員の発話 | システムの動作 |
|-------------|-------------|
| 「メイン通り123番地、工事で通行止め」 | 位置をマークし、ルートを再構成 |
| 「次のタスクはスキップ、お客様不在」 | キューから削除し、スケジュールを調整 |
| 「機材の修理が必要」 | メンテナンスチケットを作成 |
| 「タスク完了」 | 完了を記録し、次のワークフローを開始 |

配車担当への電話は不要。無線でのやり取りも不要。作業員が話し、AIが聞き取り、システムが適応します。

### 権限の階層

人間の判断がAIの推奨よりも優先されます：

```
┌─────────────────────────────────────────────────────────────────┐
│                     DECISION AUTHORITY                           │
├─────────────────────────────────────────────────────────────────┤
│                                                                  │
│   1. FIELD WORKER       ───────────────────────▶  HIGHEST       │
│      Eyes on ground, can override anything                       │
│                                                                  │
│   2. DISPATCHER         ───────────────────────▶  HIGH          │
│      Fleet-wide view, can reassign work                          │
│                                                                  │
│   3. AI OPTIMIZER       ───────────────────────▶  MEDIUM        │
│      Suggests routes/tasks, adapts to changes                    │
│                                                                  │
│   4. SCHEDULED PLAN     ───────────────────────▶  LOWEST        │
│      Starting point, always subject to reality                   │
│                                                                  │
└─────────────────────────────────────────────────────────────────┘
```

**AIは強力です—しかし、最終決定権を持つのは現場を自分の目で見ている人間です。**

### プレゼンスと通知

人間は常に対応できるわけではありません。システムは誰が対応可能かを把握しています：

| 機能 | 内容 |
|------------|--------------|
| **プレゼンス追跡** | 誰がオンラインか、オフラインか、取り込み中か |
| **ロールの認識** | 誰が承認できるか、誰がオーバーライドできるか、誰が待機中か |
| **スマートルーティング** | 通知はまず対応可能な担当者へ |
| **エスカレーション** | 一次担当者が応答しない場合、バックアップへエスカレーション |
| **確認応答** | 誰が何を見たか、いつ応答したかを追跡 |

**通知チャネル：**

- プッシュ通知（モバイル/デスクトップ）
- 重要なアラートにはSMS
- 非同期の更新にはメール
- サウンド/触覚フィードバック付きのアプリ内アラート
- チームで共有するためのキオスク表示

システムは人間の対応状況に適応します。緊急の問題は適切な担当者に届きます。緊急でない問題は、誰かが対応できるようになるまでキューで待機します。

### オフライン耐性

現場作業はネットワークが途切れる場所で行われます。それでもデバイスは動作し続けます：

- **接続が切断** → アプリはローカルのSQLiteで動作を継続
- **変更はローカルでキューに保存** → 再接続時に同期
- **データ損失なし** → Automerge CRDTが競合を処理
- **プレゼンスの更新** → オフラインとしてマークされ、通知はキューに保存

現場業務はネットワークの問題で止めるわけにはいきません。このアーキテクチャが、それを確実にします。

[現場業務の実例を見る →](/applications/logistics/)

## 接続

あなたのデータベース。あなたのスキーマ。

- データを読み込んでドキュメントに反映：「{customer.name} 様...」
- 取り込んだデータを書き戻す：フォーム送信 → あなたのテーブル
- あらゆるSQLデータベース：PostgreSQL、MySQL、SQLite
- あなたのインフラ：セルフホストまたはクラウド

**バックエンドを置き換えるのではありません。バックエンドに接続します。**

## WellKnownゲートウェイ：データ主権

公開したコンテンツはどこへ行くのでしょうか？外部プラットフォーム？そこで登場するのが**WellKnownゲートウェイ**です—他のシステム「へ」公開する場合でも、データの所有権をあなたが持ち続けられるようにします。

### プラットフォームロックインの問題

従来のアプローチ：
- 顧客データはSalesforceに
- ドキュメントはGoogle ドライブに
- フォームはTypeformに
- 各ベンダーのAPIに依存
- いずれかのベンダーが規約を変更したり、値上げしたり、サービスを終了したりすれば—大慌てすることに

### WellKnownによる解決策

```
┌─────────────────────────────────────────────────────────────────┐
│                    YOUR DATA (Source of Truth)                   │
│                                                                  │
│   SQLite on every device + NATS JetStream persistence            │
│   You own it. It's on your infrastructure.                       │
│                                                                  │
└─────────────────────────────────────────────────────────────────┘
                              │
                              ▼
┌─────────────────────────────────────────────────────────────────┐
│                    WELLKNOWN GATEWAY                             │
│                                                                  │
│   Publishes TO external platforms                                │
│   Syncs FROM external platforms                                  │
│   You control what goes where                                    │
│                                                                  │
└─────────────────────────────────────────────────────────────────┘
                              │
          ┌───────────────────┼───────────────────┐
          ▼                   ▼                   ▼
   ┌─────────────┐     ┌─────────────┐     ┌─────────────┐
   │   Google    │     │   Social    │     │  Industry   │
   │   Drive     │     │   Media     │     │  Platforms  │
   └─────────────┘     └─────────────┘     └─────────────┘
```

**基本原則：** あなたはプラットフォーム「へ」公開します。データを所有するのはプラットフォームではなく—あなたです。

### 顧客関係の主権

顧客が接するのはベンダーのブランドではなく、あなたのブランドです：

| WellKnownなし | WellKnownあり |
|-------------------|----------------|
| 顧客はベンダーのポータルにログイン | 顧客はあなた自身のポータルにログイン |
| ベンダーが関係を所有 | あなたが関係を所有 |
| ベンダーがあなたの顧客リストを保有 | あなたが顧客データを管理 |
| ベンダーの切り替え = 再構築 | ベンダーの切り替え = ゲートウェイの再接続 |

顧客はあなたとやり取りしていると思っています。実際にそうなのです。裏側の仕組みは見えません。

### インターネット標準に基づく構築

WellKnownは、メール、カレンダー、連合型ソーシャルネットワークを支えているのと同じ標準を使用しています：

| 標準 | 目的 | 例 |
|----------|---------|---------|
| **RFC 8615** | `/.well-known/` URIの検出 | `yourdomain.com/.well-known/...` |
| **WebFinger** | アカウント/リソースの検出 | ドメインをまたいでユーザーを検索 |
| **OAuth Discovery** | 認可エンドポイント | 安全なサードパーティアクセス |
| **CalDAV/CardDAV** | カレンダー/連絡先の同期 | 準拠するあらゆるアプリで動作 |
| **ActivityPub** | フェデレーションプロトコル | あらゆるシステムとの相互運用性 |

**あなたのドメインがあなたのアイデンティティです。** メール（`you@yourdomain.com`）と同じように、データはあなたが管理するURIに存在します。標準ベースのフェデレーションにより、私たちのシステムだけでなく、準拠するあらゆるシステムに接続できます。

これがオープンなWebの仕組みです。私たちはそれをパブリッシングに応用しているだけです。

### データポータビリティ

すべてが、あなたが管理する標準フォーマットに同期されます：

- **ドキュメント** → あなたのSQLiteデータベース
- **フォーム** → あなたのデータベーステーブル
- **メディア** → あなたのストレージ
- **監査ログ** → あなたのコンプライアンス記録

いつでもエクスポート。いつでも移行。囲い込まれることはありません。

## より大きな全体の一部

Publishは、統合された次元スタックの**2Dレイヤー**です—すべてWeb対応で、世界中からアクセス可能です。

### 1D → 2D → 3D スタック

```
┌─────────────────────────────────────────────────────────────────┐
│                    SINGLE SOURCE OF TRUTH                        │
├─────────────────────────────────────────────────────────────────┤
│                                                                  │
│   1D: TEXT (Markdown/DSL)                                        │
│       └── Content definition, structured data, semantic markup   │
│                          │                                       │
│                          ▼                                       │
│   2D: PUBLISH                                                    │
│       └── Web pages, documents, forms, maps, dashboards, kiosks  │
│                          │                                       │
│                          ▼                                       │
│   3D: SPATIAL                                                    │
│       └── CAD, digital twins, robotics, simulation               │
│                                                                  │
│   ALL LAYERS: Web-capable, globally accessible                   │
│                                                                  │
└─────────────────────────────────────────────────────────────────┘
```

| レイヤー | プラットフォーム | 扱う対象 |
|-------|----------|-----------------|
| **1D** | DSL/Markdown | テキストコンテンツ、構造化された定義、ソース |
| **2D** | Publish | Web、ドキュメント、フォーム、地図、キオスク、メール |
| **3D** | [Spatial](/platform/spatial/) | CAD、デジタルツイン、ロボティクス、シミュレーション |
| **共通** | [Foundation](/platform/foundation/) | オフライン同期、CRDT、NATS、デプロイ |

**すべてがWeb対応です。** 1Dのテキストが2Dの出力を駆動します。2Dの出力には3Dビューを埋め込めます。3Dモデルから2Dのドキュメントを生成できます。すべてブラウザからアクセスでき、すべて同期され、すべて同じ信頼できる唯一の情報源から生まれます。

### 連携の仕組み

ロボティクス、製造、建設など3Dで業務を行う組織に対して、Publishはドキュメントレイヤーを提供します：

- 3Dモデルから生成される**技術図面**
- アセンブリから抽出される**BOM（部品表）**
- ステップごとのビジュアル付き**作業指示書**
- CADのリビジョンに紐づく**コンプライアンスフォーム**
- 2Dチェックリスト＋3Dコンテキストによる**現場検査**

同じ信頼できる情報源。2Dと3Dの出力は常に同期されます。すべてWebからアクセス可能。
