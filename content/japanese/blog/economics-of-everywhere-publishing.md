組織を足止めし続ける問いがあります：**すべてを混乱させずに、どうやって近代化するのか？**

答えはビッグバン型の移行ではありません。完全な統合に向けて積み上げながら、各ステップで価値を生み出す段階的なアプローチです。

私はこの問題に何年も取り組んできました。その経済性が実際にどう機能するのかをご説明しましょう。

## 目標1：あらゆる場所にパブリッシングシステムを

**これが基盤です。できるだけ多くの人の手に届けましょう。**

最初の目標は一見シンプルです：コンテンツを一度作成すれば、あらゆる場所に公開できるようにすること。Web、PDF、キオスク——同じソースから、複数の出力へ。

なぜここから始めるのか？

**すぐに役立ちます。** データベース統合は不要。レガシーシステムの変更も不要。コンテンツを作成・公開するためのより良い方法、ただそれだけです。

**その悩みはどこにでもあります。** どの組織にも、Word文書、PDF、Webサイト、さまざまなシステムに散らばったコンテンツがあります。どれも内容が一致しません。更新するたびに複数の場所に手を入れる必要があります。

**導入のハードルが低い。** パブリッシングシステムを動かすRaspberry Piを設置します。作成者がコンテンツを作ります。出力はディスプレイ、Web、印刷物へと流れます。以上です。

```
Author creates content (Markdown)
         ↓
    Publish Engine
         ↓
┌────────┼────────┐
↓        ↓        ↓
Website  PDF    Kiosk Display
```

**PDFのラウンドトリップは特に強力です。** 行政機関が書式をPDFで生成します。市民がそれに記入します。スキャンして戻します。OCRがデータを抽出し、システムへとラウンドトリップさせます。

これだけでも、あらゆる行政機関が抱える大きな問題を解決します：手作業でのデータ入力が必要な紙の書式です。

キオスクのユースケースは、これをさらに広げます。同じ書式をタッチスクリーンに表示。市民が直接記入します。紙もスキャンも使わずに、データがシステムへ流れ込みます。

**3つの入力方法、同じ行き先：**
- Webフォーム → データベース
- 印刷したPDFに記入してスキャン → データベース
- キオスクのタッチスクリーン → データベース

これが目標1です。パブリッシングシステムを稼働させる。人々にコンテンツを作成してもらう。コンテンツをあらゆる画面へ届ける。

## 目標2：常時接続

**Raspberry Piにはバックホール回線が必要です。**

パブリッシングが動き始めたら、次の課題は信頼性です。インターネットがダウンしたらどうなるのか？接続が不安定な遠隔地ではどうするのか？

答えはeSIMです。

各Raspberry PiにeSIMハードウェアを取り付けます。これにより、ローカルのWiFiやイーサネットに依存しないセルラーバックホールが得られます。デバイスは常に接続経路を確保できます。

**なぜこれが重要なのか：**

- **遠隔地のキオスク**：農村部の行政サービス窓口が、地元ISPの信頼性に頼る必要がなくなります
- **フォールバック接続**：主回線に障害が起きても、eSIMが自動的に引き継ぎます
- **セキュアなチャネル**：セルラー接続は暗号化されたバックホール用に構成できます

目指すのはプログラムによるプロビジョニングです——デバイスを設置すれば、自動的に接続されます。

私たちは現在ラオスで、52か国にわたってこれをベータテストしているNGOや政府機関と協力しています。このシステムが彼らにとって特にうまく機能するのは、日時の形式、通貨の慣習、その他各組織に固有の意味的な知識を考慮したリアルタイム言語翻訳が組み込まれているからです。ここでこそローカルAIが計り知れない価値を発揮します——汎用的な翻訳サービスが見落とす文脈を理解するのです。

技術アーキテクチャ：Raspberry Pi + eSIMモジュール = 常時接続のパブリッシングノード。

## 目標3：レガシーデータベースとの統合

**いよいよ、実際のデータに接続します。**

パブリッシングが動き、接続の問題も解決すると、当然の疑問が浮かびます：「素晴らしいけれど、うちの実データはOracle/SQL Server/PostgreSQL/その他にあるんだ」

ここからがアーキテクチャの面白いところです。

パブリッシングシステムは、オリジンデータベースとしてSQLiteを使用します。これは制約ではなく、設計上の選択です。SQLiteは：
- 高速（ローカルで動作）
- 高い信頼性（実戦で鍛えられている）
- ポータブル（Pi上で動作）
- 設定不要

しかし、ここが肝心です：**SQLiteはお使いのレガシーデータベースと同期します。**

```
Publishing System (SQLite)
         ↓
    Sync Engine
         ↓
Legacy Database (Oracle, SQL Server, PostgreSQL, MySQL, etc.)
```

OracleからSQLiteまで、あらゆるものに対応するコネクタを用意しています（そう、分散構成のためのSQLite同士の同期もあります）。同期は必要に応じて双方向です。

**実際には何を意味するのか：**

既存のデータベースは変わりません。既存のアプリケーションもそのまま動き続けます。パブリッシングシステムはその隣に置かれ、データを出し入れしながら同期します。

- 製品カタログがOracleにある？パブリッシングシステムに同期して、Web/PDF/キオスクに出力
- キオスクからの顧客の送信データ？CRMに同期して戻す
- ERPの在庫更新？デジタルサイネージへ自動的に反映

**全面的な置き換えは不要。移行プロジェクトも不要。同期レイヤーがあるだけです。**

## 目標4：データ変換

**データを、正しい構造でレガシーシステムへ戻す。**

最後のピースは、パブリッシングシステムのデータを、レガシーデータベースが期待する形式へと変換して戻すことです。

これは現在、部分的に動作しています。課題は、レガシーシステムがデータ構造について独自のこだわりを持っていることです。特定のフィールド名、特定の形式、特定のリレーションを前提としています。

変換エンジンが扱うのは：
- フィールドマッピング（当社のフィールド名 → お客様のフィールド名）
- 形式変換（日付、数値、列挙型）
- リレーションの解決（外部キー、ルックアップ）
- 検証ルール（お客様のビジネスロジック）

これが完成すると、ループが閉じます：

```
Legacy Database → Sync → Publishing System → Outputs
                                ↓
                          User Input
                                ↓
Publishing System → Transform → Sync → Legacy Database
```

**データは双方向に流れます。信頼できる唯一の情報源。手作業によるデータ入力は不要です。**

## 段階的な経済性

このアプローチが経済的に成り立つ理由は次のとおりです：

### フェーズ1：即時の価値
- パブリッシングシステムを導入
- 作成者がコンテンツを作成
- 複数の出力を自動生成
- **ROI：コンテンツの重複削減、エラーの減少、時間の節約**

### フェーズ2：インフラ投資
- eSIM接続を追加
- 遠隔地や接続が不安定な場所へ展開
- 常時稼働を確保
- **ROI：カバー範囲の拡大、信頼性の向上**

### フェーズ3：統合の価値
- レガシーデータベースに接続
- 手作業によるデータ同期を排除
- 信頼できる唯一の情報源
- **ROI：データの二重入力の排除、エラーの削減、リアルタイムの正確性**

### フェーズ4：変換の価値
- ループを閉じる
- ユーザー入力がレガシーシステムへ流れる
- 完全なラウンドトリップの自動化
- **ROI：手作業によるデータ処理の完全な排除**

各フェーズが価値を生み出します。各フェーズが次のフェーズの資金となります。巨額の先行投資は必要ありません。

## 本当の目標

パブリッシングシステムを多くの人の手に届ける。人々にコンテンツを作成・公開してもらう。コンテンツレイヤーで価値を証明する。

次に接続性を加える。次に統合を加える。そして変換を加える。

**シンプルに始める。能力を育てる。ビッグバンは不要。**

これこそが、すべてを作り直す間も止まるわけにはいかない組織を近代化する方法です。
